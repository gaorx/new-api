# 01 - 总览

## 文档目标

这组文档基于当前仓库代码，对 `new-api` 的整体架构、核心概念、关键链路，以及这些概念之间的关系做一次“工程视角”的梳理。

目标不是复述 README，而是回答这几个问题：

1. 系统是怎么启动和装配起来的？
2. 后端分层各自负责什么？
3. Relay 代理的核心抽象是什么？
4. 用户、令牌、分组、渠道、能力、计费之间是什么关系？
5. 前端控制台如何映射后端这些概念？

## 一句话概括

`new-api` 本质上是一个“面向多上游 AI 提供商的统一网关 + 配额计费平台 + 管理控制台”。

它的核心不是单纯的 API 转发，而是把以下能力组合在一起：

- 统一入口协议兼容层
- 多渠道分发与故障重试
- 用户/令牌/分组权限体系
- 配额预扣、结算、退款、订阅计费
- 配置中心与动态定价
- 管理后台与运营面板

## 工程形态速记

从工程形态上说，它更像下面四类系统叠加在一起：

- 一个 AI API Gateway
- 一套 BSS / 计费系统
- 一套 IAM / 权限系统
- 一套控制台与运营后台

如果只记主线，可以记住这三条：

1. `Token / Group / Channel / Ability`
   决定请求路由到哪里。
2. `RelayInfo / Adaptor / RelayFormat`
   决定请求如何被执行。
3. `PriceData / BillingSession / Subscription / billingexpr`
   决定请求如何收费和结算。

## 顶层架构

从目录和启动过程看，项目可以分成 6 个主要子系统：

1. `router/ + middleware/ + controller/`
   负责 HTTP 接入、鉴权、限流、请求分发和 API 形态暴露。
2. `service/`
   负责业务编排，比如渠道选择、计费结算、敏感词、下载、任务轮询等。
3. `model/`
   负责数据模型、GORM 持久化、迁移、缓存同步、数据库兼容逻辑。
4. `relay/`
   负责“统一请求格式 -> 上游厂商协议”的转换与代理执行，是项目最核心的运行时子系统。
5. `setting/ + common/ + pkg/`
   负责系统配置、共享工具、表达式计费、缓存、网络、性能指标等横切能力。
6. `web/default/`
   新版前端控制台，围绕用户端、运营端、系统设置端组织页面和功能。

可以把它理解为：

```text
浏览器 / SDK / OpenAI兼容客户端
        |
        v
Gin Router + Middleware
        |
        +--> 管理 API / 用户 API / 设置 API
        |         |
        |         v
        |     Controller -> Service -> Model
        |
        +--> Relay API (/v1, /v1beta, /mj, /suno ...)
                  |
                  v
             Distribute 选渠道
                  |
                  v
            RelayInfo + Adaptor
                  |
                  v
           多上游厂商 API 请求
                  |
                  v
           Usage / Billing / Log / Metrics
```
